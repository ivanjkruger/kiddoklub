**Bilingual EN+AR rules:**
- Toggle text: "العربية / EN" — NEVER flag icons (flag = Saudi/UAE confusion)
- Toggle position: top-right in EN, top-left in AR (mirrors with layout)
- Recommended fonts: **29LT Bukra (Arabic) + Inter or Söhne (Latin)**. Avoid Tajawal (it's the Helvetica of Arabic — default tell).
- Pair Fraunces with TheMix Arabic if going editorial
- Numerals: Western digits (0-9) in BOTH languages — Qatari mums read Western digits faster on phones than Eastern Arabic
- Wrap prices in `<bdi>` to prevent QAR symbol jumping sides
- Use Tailwind v4 logical properties (`ms-`, `me-`, `ps-`, `pe-`, `start-`, `end-`) — NEVER `ml-`, `mr-`
- `dir="rtl"` on `<html>` via Next.js i18n routing, NEVER class toggle (breaks Framer Motion x-axis)
- Framer Motion: wrap directional animations in `useDirection()` hook to flip `x` sign in RTL
- MIRROR: nav, grid, card order, directional icons (arrows, chevrons)
- DO NOT MIRROR: phone numbers, prices, emails, dates in numeric format, WhatsApp icon, brand marks

**Qatari mum specifics (vs expat mum):**
- WhatsApp-first, contact form is friction
- No exposed pricing on top tier (premium = enquire)
- Majlis-aware language: "we set up in your majlis or garden" (NOT "living room")
- Hijab-aware photography: 30%+ imagery shows women in modest dress; avoid bikini-pool-party energy
- Photo permissions DEFAULT OPT-OUT for posting customer party photos to IG; explicit "we ask before we post" line is non-negotiable
- "Ladies-only setup" tag/filter for gendered events; consider female delivery-team option (verify before claiming)
- National Day (18 Dec), Garangao (mid-Ramadan kids festival), Eid Al Fitr, Eid Al Adha — themed packages drive huge bookings

**Expat mum specifics:**
- Books via Cal.com self-serve more readily
- Wants instant pricing transparency on every tier
- Reads Doha Mums FB group reviews
- Apple Pay conversion higher than Qataris (who prefer Skipcash linked to QNB/CBQ)
- Asks about insurance + allergens explicitly

## Agent 3 — Booking + payment + WhatsApp stack architecture (2026)

**The reference pattern — webhook fanout with server-authoritative state machine:**
- Cal.com is a dumb booking surface
- Supabase row is source of truth
- Vercel Edge handles `/api/webhooks/{cal,skipcash,wati}` with HMAC verification
- pg_cron handles scheduled outbound (T-2d, T-1d, T+24h)

**Three non-negotiables:**
1. **Idempotency keys table** — every external event hits it first via `INSERT ON CONFLICT DO NOTHING RETURNING`. Replay returns cached result.
2. **Postgres advisory locks** for slot races: `pg_try_advisory_xact_lock(hashtext('slot:' || $start_iso))` returns false → another tx holds it → 409.
3. **Status state machine enforced at DB** via `transition_booking()` function with `is_valid_transition()` guard. Never trust app code.

**Skipcash specifics:**
- HMAC verification: SHA-256 of `${PaymentId},${Amount},${Status},${TransactionId}` + timing-safe compare
- Two payment rows per booking (deposit + balance) linked by `booking_id`, each with separate Skipcash session — never reuse
- Refunds: under QAR 5,000 via API `/api/v1/payments/{id}/refund`; over 5K is merchant-portal manual
- Daily reconciliation at 23:00 Doha — pull Skipcash transactions, diff vs `payments` table, alert any mismatch
- **Gotcha:** Skipcash sometimes reports `Status: Paid` in webhook but settled amount differs by FX/fees on the report — reconcile on `gross_amount`, not net

**Plan B if Skipcash flakes: MyFatoorah** (cleanest swap-in, covers Qatar via QPay rails, similar HMAC pattern with `MyFatoorah-Signature` header).

**Wati template approval (2026 reality):**
- Utility templates: 1-4h approval
- Marketing templates: 24-72h, reject often
- Get utilities approved first; marketing later

**Approved utility template wording (verbatim, plug variables):**
```
Template: deposit_received_v2 (UTILITY, en + ar)
Header: Deposit confirmed — KiddoKlub
Body:   Hi {{1}}, we received your QAR {{2}} deposit for the
        {{3}} package on {{4}}. Your balance of QAR {{5}} is
        due the day before your event. Reply STOP to opt out.
Footer: KiddoKlub Doha
Buttons: [View booking] [Contact us]
```
```
Template: balance_due_v2 (UTILITY)
Body: Hi {{1}}, friendly reminder — your balance of QAR {{2}}
      for tomorrow's {{3}} party is due today. Tap below to pay.
Buttons: [Pay balance] (URL with {{4}})
```

**Opt-in language Meta wants in our booking form:**
> "By booking, you agree to receive WhatsApp confirmations, reminders, and party updates from KiddoKlub. Reply STOP anytime."

**24-hour conversation window mechanics:**
- Customer sends → 24h customer service window opens → free-form OK inside
- Always assume scheduled sends are OUTSIDE the window → always use template
- Don't try to game the window; Meta is wise to it and rate-limits

**Cal.com architecture decision: 3 SEPARATE event types** (mini, classic, signature), NOT one with package as custom field. Better URLs for ads (`cal.com/kiddoklub/classic`), Cal.com's availability engine handles cleanly, separate buffers per package.

**Schema refinements vs my v1 (Council 3 wins on these):**
- Separate `payments` table (NOT amount fields on `bookings`) — supports deposit + balance + refund as separate rows
- `idempotency_keys` table at the front of every webhook handler
- `audit_log` table with trigger on bookings/payments updates
- Security-definer function `get_available_slots(start, end)` returning slot ranges for anon — NEVER expose `bookings` to anon

**3 most expensive bugs:**
1. Double-booking same slot — fix: pre-confirm webhook + advisory lock + 4xx back to Cal.com
2. Charging deposit twice — fix: unique `(booking_id, payment_type)` + reuse existing PaymentUrl if pending row exists
3. Sending balance-due WA after customer paid — fix: cron filter `status = 'deposit_paid' AND NOT EXISTS (payment WHERE type='balance' AND status='paid')`, recheck inside transaction

**Telemetry from Day 1:**
- Sentry (errors), BetterStack (uptime, 60s checks), Vercel logs (HTTP), Supabase audit_log (business state), Telegram bot (human alerts)
- Webhook 5xx >2% over 5min → Telegram
- Skipcash recon mismatch → Telegram + email
- Wati template send failure → Telegram
- Booking → deposit conversion <60% over 7d → review
- Site uptime: 2 consecutive fails → SMS + Telegram
- Bookings stuck in `pending_deposit` >2h → Telegram (chase or refund)
